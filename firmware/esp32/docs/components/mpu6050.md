## Overview

The MPU6050 is FallHelp's main IMU. It uses accelerometer and gyroscope data to detect impact, tilt angle, and posture change of the wearer.

This document is the owner doc for the MPU6050 and the fall detection core. It is not the lab manual of the Fall Detection Sensor Lab.

---

## Calibration

Goals after calibration:

1. `SVM = sqrt(ax^2 + ay^2 + az^2) ≈ 1.0g` while the device is still
2. Gyro drift close to 0 while the device is still
3. Offset values consistent with the real worn position

Enable calibration mode in `firmware/esp32/src/sensor_tuning/MPU6050_Sensor.ino`:

```cpp
#define SOFTWARE_CALIBRATION_MODE true
```

Steps:

1. Hang the device around the neck in the real usage position
2. Stand still and upright
3. Wait for the 3-second warmup countdown
4. Let the firmware collect 400 samples
5. Copy the printed `MPU_CAL_*` values into the code
6. Set `SOFTWARE_CALIBRATION_MODE` back to `false`

Calibration values currently locked in the firmware:

```cpp
#define MPU_CAL_ACCEL_OFFSET_X_MS2  1.185f
#define MPU_CAL_ACCEL_OFFSET_Y_MS2  2.329f
#define MPU_CAL_ACCEL_OFFSET_Z_MS2 -0.159f
#define MPU_CAL_GYRO_OFFSET_X_RAD  -0.059f
#define MPU_CAL_GYRO_OFFSET_Y_RAD   0.029f
#define MPU_CAL_GYRO_OFFSET_Z_RAD  -0.017f
```

These values are used by both `main_firmware` and `sensor_tuning`. Do not change them unless the mounting position changes or there is a new calibration round with complete evidence.

## swCal vs hwOff

| Item | swCal | hwOff |
| --- | --- | --- |
| Where values are stored | `MPU_CAL_*` in source | hardware register in the MPU6050 |
| Where applied | after the I2C read in firmware | before values leave the IC |
| Used in FallHelp | Yes | No |

FallHelp intentionally uses software calibration so the values are easy to inspect and sync across firmware variants.

## Runtime Behavior

Fall detection core:

```text
read accel + gyro
  -> complementary filter computes pitch/roll
  -> SVM detects impact magnitude
  -> postureDelta checks posture change after impact
  -> duration gate confirms timing
  -> suspected_fall
  -> cancel window
  -> fall_cancelled or fall_confirmed
```

Main values in the current firmware:

| Value | Current | Purpose |
| --- | --- | --- |
| Impact threshold | `2.0g` default | Impact gate from SVM |
| Duration threshold | `1500 ms` default | Gate for impact timing/waiting for stabilization |
| Posture threshold | `45 deg` default | Gate for posture change after impact |
| Cancel timeout | `15000 ms` | Wait for the wearer to press cancel after `suspected_fall` |

`main_firmware` uses a fixed cancel window from `FallDetectionConfig.ino` and no longer uses a separate runtime profile.

## SVM And Posture Delta

SVM:

```text
SVM = sqrt(ax^2 + ay^2 + az^2)
```

Used to look at the magnitude of the resultant force from the accelerometer, regardless of the device orientation.

postureDelta:

```text
postureDelta = posture difference around impact window
```

Used to separate forceful activities that are not falls from fall-like posture changes.

Examples:

| Case | SVM | postureDelta | Expected result |
| --- | --- | --- | --- |
| Sideways fall | above threshold | above threshold | `suspected_fall` |
| Sitting down hard | may be high | low | no trigger |
| Fast walking | may have spikes | low | no trigger |
| Fall too gentle to exceed threshold | low | not enough to decide | no trigger |

## Diagnostic Log vs Fall Detection Log

Diagnostic log:

```text
[abnormal] accel=(x,y,z)g gyr=(rx,ry,rz)rad/s swCal=(dx,dy,dz) fsRange=...
```

Used to look at calibration, sensor range, and abnormal values from the IMU. It is not evidence that the firmware detected a fall.

Fall detection log:

```text
[fall] svm=X.XXg postureDelta=XX.Xdeg -> suspected_fall / cancel / confirm
```

Used to look at the decision path of the fall flow.

## Serial Commands And Safety

The `mpu on` command enables the IMU diagnostic stream and disables fall detection in that mode.

| State | Fall detection | Use when |
| --- | --- | --- |
| `mpu on` | off | debugging raw IMU only |
| `mpu off` or normal mode | on | fall/ADL tests and runtime flow |

Do not use `mpu on` during a fall/ADL session where you need the firmware to generate `suspected_fall` or `fall_confirmed`.

## Test Checklist

### Calibration Check

1. Use `sensor_tuning`
2. Set `SOFTWARE_CALIBRATION_MODE true`
3. Wear the device in the real position
4. Collect 400 samples
5. Pick the round whose magnitude is closest to `1.0g`

### Fall Core Check

1. Use the firmware variant you want to test
2. Confirm that `mpu on` is not enabled
3. Run `sim fall` or the defined test round
4. Look at SVM, postureDelta, and which gates passed/failed in the Serial log
5. For the system flow, confirm `suspected_fall -> fall_cancelled / fall_confirmed`

### Fall Detection Sensor Lab Boundary Check

1. Use only `sensor_tuning` for Basic Activity Collection
2. Use the detailed workflow in `fall_detection_sensor_lab/`
3. Do not draw statistical conclusions from this dataset

## Troubleshooting

### Fall Not Detected

Check:

1. Is `mpu on` disabling fall detection?
2. Is SVM below the impact threshold?
3. Is postureDelta below the threshold?
4. Is the calibration offset wrong for the real worn position?
5. Are the firmware variant and build profile correct?

### Frequent Triggers During Normal Activities

Check:

1. Is calibration skewing the baseline SVM?
2. Is the postureDelta threshold too low?
3. Does the device move on the neck more than in real use?
4. Were multiple values changed in one round, making it impossible to trace back?

### Incomplete Cancel / Confirm Flow

Check:

1. Is the GPIO27 button ready?
2. Is the cancel timeout still `15000 ms`?
3. Does AlertSystem reset state at the right time?
4. Is MQTT connected, if you need to see the event on the backend side?

### Sensor Lab CSV Not As Expected

Check:

1. Are you using `sensor_tuning` and the topic `device/+/lab/imu`?
2. Is the Node-RED Dashboard actually in the Fall Detection Sensor Lab workflow?
3. Check the CSV schema and trial rules in `fall_detection_sensor_lab/`, not this file
